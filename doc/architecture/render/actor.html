Subject: outline an event model for an autonomous stage executor

namespace trifecta.stage

Actor

To perform a sequence of Scene comprising a stage for some duration 100ms <= tx <= 5s, while responding to changes in conditions, an autonomous Actor will operate on its own thread and coordinate events under a single instance-specific lock. All actions will be trivial except when performing a Scene that involves significant continuous computation. Responsiveness to concurrent events during computation will depend on granularity of the computation steps; for example, if a Scene performs computation in 10ms loop iterations, then events relevant to the Actor may go unnoticed for as long as 10ms. For a Scene that consumes one or more resources and does not perform computation, it is assumed that the Actor remains passively available for event notification while each resource performs work on a separate driver thread.

When not performing computation, an Actor is either busy with a trivial event while holding its lock, or waits on its lock until some notification occurs. Implementation can most likely use a simple Monitor, which can be held privately within Actor. Events will arrive over interface callbacks, which Actor can implement as synchronizing on its Monitor. Before initiating a wait phase, Actor will discover any state changes on subscribed event sources; if found, no wait will occur and Actor will directly respond.

Appearance

Each time an Actor queues for resources it presents a fresh Appearance, which is what the resource queues hold and to which they Grant() the resource.. When an Actor leaves a queue (for example, on stop) it simply discards its Appearance; a queue that later finds a stale Appearance recognizes it as a ghost and skips it, precluding the need to remove abandoned resource requests from the queue.
